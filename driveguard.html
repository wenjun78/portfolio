Signature build / End-to-end ML engineering on Databricks

DriveGuard.

Which hard drives in a fleet should an operator inspect or replace this week, before they fail? DriveGuard answers that on real hardware telemetry — Backblaze's daily SMART snapshots of roughly 300,000 production drives — as a complete ML system: PySpark medallion tables, a 30-day failure label that respects right-censoring, a time-ordered evaluation that cannot leak, an XGBoost ranker measured at a fixed alert budget against the rule operators already use, MLflow and Unity Catalog lifecycle with a champion gate, daily alerts with reason codes, drift and matured-label monitoring, and retraining that runs only when the monitor says so. It deploys as a Databricks Asset Bundle on serverless compute and runs on Free Edition.

01 / The problem

A ranked list with a budget, not a probability.

Storage teams do not act on probabilities; they act on a short list they can work through with the people, spare drives and maintenance windows they have. So the deliverable is a daily ranking of the fleet, the top 0.5% flagged, and every number reported is measured at that budget: how many of the drives about to fail were on the list, how clean the list was, how many days of warning the first alert gave, and how much noise healthy drives generated. The bar to clear is the rule Backblaze itself gives operators — watch five SMART counters — put through the identical evaluation.

01 / LABEL

Fails within 30 days, censoring respected

A drive-day is positive if the recorded failure lies in the next 30 days, and negative only when the drive is observed surviving the whole window. Drives that leave the fleet or hit the end of the data before the window closes are censored — kept for scoring, excluded from training and metrics — instead of being labelled healthy. The failure-day row itself is the outcome, not a decision point, and is excluded too.

02 / FEATURES

A function of the past only

Rolling deltas, non-zero-day counts and extremes of the key counters over 7 and 30 calendar days (range frames on the day number, because drives have gaps and row-count windows silently change meaning), power-on hours, temperature, workload and wear counters, model and capacity. No feature grows with calendar time. A test deletes the future and asserts every feature is unchanged.

03 / EVALUATION

Time-ordered, label-disjoint

Train, validation and test are consecutive periods separated by 30-day unlabeled gaps, so a training row's label can never depend on an outcome inside the validation period. An optional holdout of whole drive models reports transfer to populations the model never saw — the question a real fleet asks every quarter.

02 / Architecture

One package, three entry points: CLI, notebooks, tests.

Everything lives in one Python package driven by environment variables. The same wheel runs on a laptop with Parquet and a local MLflow store, in CI on local Spark, and inside Databricks jobs with Delta, Unity Catalog and the workspace tracking server. The notebooks only pass widgets through; nothing is rewritten between environments.

04 / Engineering decisions

The parts a reviewer should push on.

DECISION 01

Censored, not zero

The naive label — "no failure in 30 days ⇒ healthy" — teaches a model that disappearing looks like health, because decommissioned drives and the last month of data all become negatives. Roughly a quarter of rows in a one-year window are censored; they are scored in production and ignored in metrics.

DECISION 02

Gaps equal to the horizon

Feature-disjoint splits are not enough when labels look forward. A training row on the last training day carries a label that reads 30 days into validation. Thirty-day unlabeled gaps make the periods label-disjoint; the split module refuses histories too short to afford them.

DECISION 03

Weighted negatives, driver-side training

All positives plus twenty negatives per positive, with weights that restore the fleet's prior. Training stays small at any fleet size, probabilities keep their meaning (so Brier and the score-distribution PSI are interpretable), and scoring — the part that has to touch every drive — is the part that is distributed.

DECISION 04

The reference travels with the model

Drift is measured against an unbiased sample of the fleet the champion was trained on, stored inside the model artefact — not against the rebalanced training set (which would make every healthy day look drifted) and not against whatever a table held last week.

DECISION 05

Promotion is a gate, not a default

Every run registers a Unity Catalog version. The @champion alias moves only when validation PR-AUC is at least the incumbent's, read from the incumbent's own run. Scoring and monitoring always resolve the alias, so a worse retrain can never silently take over.

DECISION 06

Matured labels close the loop

Each monitoring run back-fills real precision, recall and lead time for every past snapshot whose 30 days have elapsed. Retraining is triggered by evidence — several key features past PSI 0.2, or matured recall below the floor — exposed as a job task value that a Databricks condition task reads.

Scope and limitations

Data is Backblaze Drive Stats, used with attribution. The first deployment target is Databricks Free Edition: serverless compute only, CPU-only serving, a cap on concurrent job tasks — the bundle is a straight line of tasks and the serving endpoint is a small CPU one with scale-to-zero.

  • Training is driver-side on the weighted sample; it is the right trade for a tabular model at fleet scale, but it is not distributed training.
  • Free Edition quotas mean "subset first": whole drive histories for a hash-selected share of serials, so lifecycles, labels and censoring stay intact. The code is identical at 100% of the fleet; the compute is not.
  • The synthetic fixture exists for tests and dry runs. Nothing computed from it is a result.
  • The operational surface is the batch alert table; the endpoint serves the champion for on-demand checks.

05 / The console

A live window onto the pipeline, not a slide about it.

The fleet console reads the pipeline's own outputs from the Databricks workspace — Unity Catalog tables through the SQL warehouse, the registered model through MLflow, job runs through the Jobs API, the champion through Model Serving — and shows what an operator and an ML engineer would each look at: today's ranked list with reason codes and, once a snapshot's 30 days have elapsed, what actually happened to every flagged drive; matured recall, precision and lead time over time; PSI drift and each retraining decision; model versions and the champion's evaluation against the operator rule; and a what-if scorer. Reads are cached with stale-while-revalidate so a public page stays inside Free Edition's quota, and when the workspace is asleep or absent the console degrades to a bundled snapshot and says so on every page — it never presents demo numbers as live ones.

REPLAY

The fleet moves

Backblaze publishes history, so the daily job runs on a replay clock: one data-day per real day. Matured outcomes catch up day by day, drift accumulates as the fleet ages, and the retrain gate can fire for real.

HINDSIGHT

Every alert gets graded

Alerts per day are split into drives that did fail within the horizon, drives that stayed healthy, and outcomes still pending — the same budgeted precision and recall the training evaluation reports, now on live snapshots.

ONE CODE PATH

Snapshot = live, by construction

The demo snapshot is exported by running the live source's own queries through DuckDB over the local tables. The console cannot drift from the pipeline because there is nothing to drift: same shapes, same SQL.

06 / In practice

Two commands on a laptop, two on Databricks.

pip install -e ".[local,dev,app]"
make fixture && make demo          # synthetic fleet: bronze → silver → gold → train → 45-day scoring replay → monitor
make console                          # the fleet console on localhost:8000 (demo snapshot until Databricks is configured)
python scripts/download_backblaze.py --quarters 2024Q3 2024Q4 2025Q1 --serial-frac 0.10 --out data/raw
databricks bundle deploy -t dev && databricks bundle run -t dev driveguard_build

Or nothing on a laptop at all: two repository secrets and one click on the databricks-bootstrap workflow download the Backblaze subset on a GitHub runner, load the Volume, deploy the bundle, run the build job and commit the console snapshot; the daily workflow then operates the system on a schedule. The repository holds the package, the fleet console (FastAPI, Render blueprint, Dockerfile), seven Databricks notebooks, the Asset Bundle with a one-off build job and a scheduled daily job (ingest → features → score → monitor → condition → retrain), the Backblaze downloader with serial-hash subsetting, the fixture generator, a results reporter, 27 tests covering label semantics, censoring, time safety, schema drift, splits, budgeted metrics, PSI, the console API and a full end-to-end run, and a CI workflow that runs them on local Spark and builds the wheel.
