01 / The idea

Turn a static CV into a searchable conversation.

Ask WJ isn't an open-ended chatbot trained to invent answers about its owner. It retrieves structured Markdown notes, combines relevant context with a controlled prompt, and returns grounded answers with traceable source references. Visitors can rate answers; the owner can audit what happened and improve the knowledge or prompt.

01 / RETRIEVE

Retrieval agent

A LangGraph graph runs before the model: classify the intent, condense a follow-up with the previous question, retrieve with BM25 and dense embeddings fused by reciprocal rank fusion, grade each hit, and rewrite-and-retry once when nothing is relevant. Deterministic nodes, so no model call before the first streamed token.

02 / RESPOND

Cited, streamed answers

OpenAI-compatible model API, streaming responses, contextual conversation history and citations back to the underlying notes. English and Chinese page options.

03 / IMPROVE

Inspectable RAG

Owner dashboard for question and visitor trends, retrieved-context traces, prompt versions, feedback, knowledge edits and retrieval experiments.

02 / Architecture

Deliberately simple where it counts.

The knowledge collection is small enough for an in-memory index rather than a managed vector database. State and audit records are stored in SQLite locally or PostgreSQL in hosted environments.

04 / Engineering decisions

Built for evaluation, not just a demo.

TESTABILITY

Offline tests + CI

Unit and API tests with a fake model, retrieval fixtures with an 80% minimum hit-rate gate, lint/format checks, PostgreSQL tests and a Docker health check are defined in GitHub Actions.

GUARDRAILS

Operational controls

Admin token, rate and message limits, security headers, IP hashing, explicit visitor logging disclosure and optional retention cleanup.

ITERATION

Versioned prompts

Knowledge editing, prompt draft tests, version history and rollback, together with question ratings and retrieved-note traces.

Scope and limitations

This is a personal RAG application with a public Render app link. The live endpoint is shared by the project owner; uptime, real-user adoption and commercial impact have not been independently verified. A sleeping free-tier host may take time to wake.

  • The 80% threshold is a retrieval CI gate, not a reported measured accuracy score.
  • Grounding relies on retrieved context and prompt guidance; there is no independent second-model factual checker.
  • Indexing and rate limits are per process, and the repository does not yet include database migrations or visitor accounts.

05 / Design rationale

Why this architecture fits the problem.

The requirement was more specific than building a generic chatbot: help a visitor find verifiable facts about one person, reduce unsupported claims, and give the owner enough evidence to fix retrieval or prompt failures. That shaped the design.

DECISION 01

Hybrid retrieval over a small corpus

Visitors ask both exact-name questions and broader questions such as what experience relates to secure AI applications. BM25 finds exact terms, embeddings handle alternative phrasing and RRF merges both. The corpus is small enough to hold in process, avoiding a separate vector database and its operating cost.

DECISION 02

One deterministic retrieval agent

The LangGraph workflow classifies intent, combines follow-up context, retrieves, grades relevant chunks and performs at most one corrective rewrite. Keeping these steps deterministic avoids extra pre-answer model requests; an OpenAI-compatible model generates the streamed answer once context is selected.

DECISION 03

Auditability before optimisation

Per-question traces record retrieved notes, ranks, cited sources, prompt versions, latency and token usage. Ratings and knowledge editing support iterative improvement; input limits, rate caps, IP hashing and an admin token help manage privacy, access and operating cost. Citation support is not a guarantee of factual correctness.

06 / Evidence, impact & limitations

What was actually demonstrated.

VERIFIABLE

Tests, not invented usage figures

The repository has offline retrieval fixtures, unit/API tests and CI. An 80% retrieval-hit-rate threshold is a configured build gate—not a claimed live accuracy percentage. The source also includes a Render/Neon deployment path and a public app URL; that alone is not evidence of traffic or adoption.

INTENDED IMPACT

Less searching, clearer evidence

Visitors can ask a question instead of manually reading project pages, while the owner can see where a retrieval failed and revise the source notes or prompt. The design supports recruiter-facing discovery and technical demonstration. No measured reduction in browsing time, user conversion or support cost is claimed.

HONEST LIMITS

What remains unproven

There is no independent answer-verification model; grounding relies on retrieval, prompts and auditable citations. Search and rate-limit state are local to one process, and database migrations are not included. A formal evaluation of answer factuality, production reliability and multi-instance scaling would be further work.
