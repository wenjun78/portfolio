BI Copilot.

Ask a sales warehouse "top 5 customers by gross margin last quarter" and get the number, the SQL that produced it, the rows and a chart—from a team of LangGraph agents that never guess what "revenue" means, because a semantic layer tells them.

01 / The idea

Text-to-SQL fails on meaning before it fails on syntax.

"Revenue" with cancelled orders in it, "Q1" read as calendar Q1, "region" taken from the sales rep instead of the customer: these are the mistakes that make business users stop trusting a chatbot. BI Copilot puts a governed semantic layer between the question and the database. Every metric's expression, mandatory filter and fiscal rule lives in one YAML file; the agents resolve language to those definitions, a deterministic compiler emits a correct draft, and the model refines rather than invents.

01 / PLAN

Planner agent

Field mapping from phrases to metric and dimension ids, filter values, fiscal and relative time ("last quarter" against an as-of date), top-N and YoY/QoQ. Ambiguous phrases ("margin") become a clarifying question with options instead of a guess.

02 / QUERY

SQL agent

A ReAct loop with bound tools (describe a table, sample a column's values, validate a draft), then writes from the compiler draft plus observations and passes a guard (single SELECT, table allowlist, LIMIT, dialect transpile) and a read-only executor. Errors come back as observations and the agent repairs, at most twice.

03 / EXPLAIN

Analyst + critic

The analyst writes the business answer, insights and a chart spec from the rows; the critic checks it against the question, plan, SQL and data, and can send the supervisor back to the SQL agent with a concrete fix.

02 / Architecture

Three agents, one shared state, one supervisor.

Each agent is its own compiled LangGraph sub-graph added as a node of a supervisor graph, so it can be tested, traced and swapped on its own. Patterns in use: Plan-and-Execute (planner), a ReAct-style tool loop with repair (SQL agent) and Reflection (critic). Runs with zero infrastructure (SQLite, in-memory vectors, no API key) and with Postgres + pgvector + a model, on the same code path.

03 / Interface

Answer, chart, SQL and the trace behind them.

The static demo on this site presents precomputed outputs for the 60-question evaluation set (answer, SQL, rows, chart and trace). It is a static, server-free showcase, not a live LLM session. The full application includes a runnable FastAPI service and React UI.

04 / Engineering decisions

Measured, not demoed.

EVALUATION

Execution accuracy

60 questions, 50 with hand-written gold SQL. The harness runs both and compares result sets, not SQL strings, and reports by tag (breakdown, top-N, trend, comparison, relative time, clarify, refuse). The repository reports 100% execution accuracy for the deterministic no-key path on the gold-SQL questions; the LLM-backed path requires separate measurement.

GOVERNANCE

Semantic layer as contract

11 metrics, 16 dimensions with aliases and allowed values, 6 business rules and an ambiguity map in one YAML file. Prompts, compiler and eval all read it; changing a definition is a one-line edit, not a prompt hunt.

INTEROP

Agent-to-agent, on a schedule

Agent Card at /.well-known/agent.json and JSON-RPC message/send returning a task with text and data artifacts. A second agent with no database access compiles a briefing from it; a weekly GitHub Actions job runs it and commits the report.

Scope and limitations

The warehouse is synthetic and generated from a fixed seed; shapes are realistic, values are not. This is a working, tested system, not a claim of production adoption.

  • The 100% figure refers solely to the deterministic compiler on the gold-SQL questions. It is not a measured accuracy score for an LLM-backed workflow.
  • Multi-fact metrics (attainment vs targets) and window functions are left to the model path; the compiler covers breakdowns, filters, time, top-N and YoY/QoQ.
  • The A2A surface implements the Agent Card and message/send shape, without streaming or push notifications. Per-user row-level security is not yet implemented.

05 / Design rationale

Why these choices—not just a list of frameworks.

The central engineering problem was not whether an LLM could produce syntactically valid SQL. It was whether a business user could trust the meaning of the result and inspect how it was produced. Three decisions are central to the design.

DECISION 01

Semantic definitions before generation

Free-form text-to-SQL can silently count cancelled orders as revenue, apply calendar instead of fiscal quarters or join the wrong region. A YAML semantic layer specifies metric expressions, aliases, filters and fiscal rules. The deterministic compiler makes a baseline query from those definitions before any model refinement, trading some flexibility for consistent business meaning.

DECISION 02

Retrieve, then rerank and inspect

Keyword retrieval helps with exact metric and table names; embeddings help when users phrase requests differently. Structured resolver hits keep key metadata in context. Reciprocal rank fusion combines the signals, then a lexical, FlashRank or LLM reranker narrows the context. The trace exposes which evidence was retrieved so incorrect field mappings can be investigated.

DECISION 03

Bounded tools and guarded execution

Instead of trusting the generated SQL, the SQL agent can inspect table metadata through read-only tools. sqlglot parsing, statement restrictions, a table allowlist, row caps and timeouts constrain execution; a limited repair loop handles failed attempts. Redis or in-process caching avoids repeated work while including a semantic-version key to prevent stale answers after metric changes.

06 / Evidence, impact & open questions

A verifiable prototype, not a claimed business rollout.

EVIDENCE

50 gold SQL cases

The 60-question set contains 50 hand-written gold SQL examples plus clarification/refusal cases. Results are compared by executed output rather than SQL-string equality. The reported 100% deterministic execution accuracy supports the baseline compiler in this synthetic setup; it does not demonstrate LLM generalisation or deployment performance.

INTENDED IMPACT

More auditable self-service BI

The system demonstrates how a business user could ask for a metric and inspect its exact definition, SQL, retrieved context, rows and chart rather than rely on an opaque answer. A second reporting agent uses the A2A endpoint to assemble a briefing without direct database access. Time saved, adoption and financial return were not measured.

NEXT VALIDATION

What would make it production-ready?

Measure LLM execution accuracy separately; test ambiguous and adversarial requests against real access policies; add caller-specific row-level security; test latency, cost, query loads and operational recovery; and expand the deterministic compiler beyond a single star schema to complex multi-fact analytics.

The case study documents the problem, architecture, design decisions, evaluation methodology and remaining validation work. No production customer usage is asserted.
