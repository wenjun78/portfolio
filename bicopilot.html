Signature build / Multi-agent intelligent BI

BI Copilot.

Ask a real e-commerce warehouse (Olist, 99,441 Brazilian orders) "top 5 categories by revenue last quarter" and get the number, the SQL that produced it, the rows and a chart—from a team of LangGraph agents that never guess what "revenue" means, because a semantic layer tells them. Then open the SQL console, the data dictionary, export the rows, or paste a PDF and ask about it.

01 / The idea

Text-to-SQL fails on meaning before it fails on syntax.

"Revenue" with canceled orders in it, "customers" counted on per-order IDs instead of people, "state" taken from the seller instead of the buyer: these are the mistakes that make business users stop trusting a chatbot. BI Copilot puts a governed semantic layer between the question and the database. Every metric's expression, mandatory filter and calendar rule lives in one YAML file; the agents resolve language to those definitions, a deterministic compiler emits a correct draft, and the model refines rather than invents.

01 / PLAN

Planner agent

Field mapping from phrases to metric and dimension ids, filter values, calendar and relative time ("last quarter" against the as-of date 2018-08-31), top-N ("worst" follows bad-is-high metrics) and YoY/QoQ. Text pasted from a PDF or screenshot joins the question. Ambiguous phrases ("delivery", "performance") become a clarifying question with options instead of a guess.

02 / QUERY

SQL agent

A ReAct loop with bound tools (describe a table, sample a column's values, validate a draft), then writes from the compiler draft plus observations and passes a guard (single SELECT, table allowlist, LIMIT, dialect transpile) and a read-only executor. Errors come back as observations and the agent repairs, at most twice.

03 / EXPLAIN

Analyst + critic

The analyst writes the business answer, insights and a chart spec from the rows; the critic checks it against the question, plan, SQL and data, and can send the supervisor back to the SQL agent with a concrete fix.

02 / Architecture

Three agents, one shared state, one supervisor.

Each agent is its own compiled LangGraph sub-graph added as a node of a supervisor graph, so it can be tested, traced and swapped on its own. Patterns in use: Plan-and-Execute (planner), a ReAct-style tool loop with repair (SQL agent) and Reflection (critic). Runs with zero infrastructure (SQLite, in-memory vectors, no API key) and with Postgres + pgvector + a model, on the same code path.

03 / Interface

Answer, chart, SQL and the trace behind them.

The live app runs on Render's free tier, so the first question after a quiet spell waits for the server to wake; the copy on this site answers from a precomputed bundle of the 60 evaluation questions meanwhile. Three tabs: Chat (answer, chart, table, SQL, trace, export, "open in SQL console", paste or drop a PDF, image or CSV as context), SQL console (schema browser from the dictionary, history, the same guard and executor as the agents, "explain with the analyst agent", export) and Data dictionary (every column's business meaning, live profile, which metrics use it, masked flags). A role switch (analyst / viewer) and a "new chat" reset sit in the header; previous turns travel with each question so follow-ups and clarification replies resolve.

04 / Engineering decisions

Measured, not demoed.

EVALUATION

Execution accuracy

60 questions, 50 with hand-written gold SQL. The harness runs both and compares result sets, not SQL strings, and reports by tag (breakdown, top-N, trend, comparison, relative time, clarify, refuse). The repository reports 100% execution accuracy for the deterministic no-key path on the gold-SQL questions; the LLM-backed path requires separate measurement.

GOVERNANCE

Semantic layer as contract

20 metrics, 17 dimensions with aliases and allowed values, 8 business rules, two base tables with ordered joins and an ambiguity map in one YAML file, plus a column-level data dictionary. Prompts, compiler, console, eval and the viewer mask all read them; changing a definition is a one-line edit, not a prompt hunt.

INTEROP

Agent-to-agent, on a schedule

Agent Card at /.well-known/agent.json and JSON-RPC message/send returning a task with text and data artifacts. A second agent with no database access compiles a briefing from it; a weekly GitHub Actions job runs it and commits the report.

Scope and limitations

The data is Olist's public Brazilian e-commerce dataset (Kaggle, CC BY-NC-SA 4.0): one company, 2016 to 2018, amounts in BRL, review text in Portuguese. The loader builds a star schema and resolves the source's master-data problems (a golden customer record merges 99,441 per-order IDs into 96,096 people; duplicate reviews; 610 uncategorised products). This is a working, tested system on real data, not a claim of production adoption.

  • The 100% figure refers solely to the deterministic compiler on the gold-SQL questions. It is not a measured accuracy score for an LLM-backed workflow.
  • The compiler covers breakdowns, filters, time, top-N and YoY/QoQ on one base table, pivoting order-grain metrics to item grain for product and seller slices; anything beyond that is left to the model path. Relative periods are pinned to the as-of date 2018-08-31.
  • Image attachments need a vision-capable model key; the SQL console, dictionary and attachments need the live API, so the static fallback is chat only.
  • The A2A surface implements the Agent Card and message/send shape, without streaming or push notifications. Per-user row-level security is not yet implemented.

05 / Design rationale

Why these choices—not just a list of frameworks.

The central engineering problem was not whether an LLM could produce syntactically valid SQL. It was whether a business user could trust the meaning of the result and inspect how it was produced. Three decisions are central to the design.

DECISION 01

Semantic definitions before generation

Free-form text-to-SQL can silently count canceled orders as revenue, count the raw per-order customer IDs as customers or take the state from the seller. A YAML semantic layer specifies metric expressions, aliases, filters and calendar rules, and says that "customers" means golden records. The deterministic compiler makes a baseline query from those definitions before any model refinement, trading some flexibility for consistent business meaning.

DECISION 02

Retrieve, then rerank and inspect

Keyword retrieval helps with exact metric and table names; embeddings help when users phrase requests differently. Structured resolver hits keep key metadata in context. Reciprocal rank fusion combines the signals, then a lexical, FlashRank or LLM reranker narrows the context. The trace exposes which evidence was retrieved so incorrect field mappings can be investigated.

DECISION 03

Bounded tools and guarded execution

Instead of trusting the generated SQL, the SQL agent can inspect table metadata through read-only tools. sqlglot parsing, statement restrictions, a table allowlist, row caps and timeouts constrain execution; a limited repair loop handles failed attempts. The SQL console goes through the same guard. The viewer role is enforced three ways (SQL rewrite on the AST, row post-filter, prompt note), so a masked column cannot reach the screen or an export. Redis or in-process caching keys on question, role and semantic-layer version so a definition change never serves a stale answer.

06 / Evidence, impact & open questions

A verifiable prototype, not a claimed business rollout.

EVIDENCE

50 gold SQL cases

The 60-question set contains 50 hand-written gold SQL examples plus clarification/refusal cases. Results are compared by executed output rather than SQL-string equality. The reported 100% deterministic execution accuracy is for the baseline compiler on the real Olist warehouse; it does not demonstrate LLM generalisation or deployment performance.

INTENDED IMPACT

More auditable self-service BI

The system demonstrates how a business user could ask for a metric and inspect its exact definition, SQL, retrieved context, rows and chart rather than rely on an opaque answer. A second reporting agent uses the A2A endpoint to assemble a briefing without direct database access. Time saved, adoption and financial return were not measured.

NEXT VALIDATION

What would make it production-ready?

Measure LLM execution accuracy separately; test ambiguous and adversarial requests against real access policies; extend column masking to caller-specific row-level security; test latency, cost, query loads and operational recovery; and expand the deterministic compiler beyond a single star schema to complex multi-fact analytics.

The case study documents the problem, architecture, design decisions, evaluation methodology and remaining validation work. No production customer usage is asserted.
